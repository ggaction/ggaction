## 제안

기존 createData/reviseData의 원본 행과 dataset schema 필드 이름에는 빈 문자열을 허용한다. 별도 옵션·이름 변경·열 삭제는 추가하지 않는다. schema version은 1을 유지하고, 이름은 입력 문자열 그대로 저장한다. 현재 허용되는 공백 이름도 자르거나 바꾸지 않는다. 필드 이름의 중복, 타입·nullable·optional, 선언하지 않은 열 검사는 유지한다.

차트의 field 바인딩, 필터·계산·집계의 입력 필드, 새로 생성하는 필드 이름, 데이터·마크·척도 ID는 기존의 비어 있지 않은 문자열 규칙을 유지한다. 빈 키는 저장할 수 있지만 차트에서 새로 참조할 수 없다. 이 경계는 공용 식별자 검증기를 완화하지 않고 원본 스키마 이름의 경계에서만 구현한다.

```js
chart().createData({ values: [{ x: 1, y: 2, "": "원본 셀" }] });
// semanticSpec.datasets[0].values[0][""] === "원본 셀"
// inferred schema에도 name:""가 남는다.
```

명시 schema도 name:""를 포함하면 같은 행을 저장할 수 있다. 명시 schema에서 빈 열을 빼면 종전처럼 undeclared field 오류다. createData 호출·옵션 수는 바뀌지 않는다.

## 생명주기와 호환성

입력 객체와 이전 프로그램의 불변성을 유지한다. 행을 보존하는 filter/sort/computed/window/revision은 빈 셀과 스키마를 함께 유지한다. summary/fold/pivot 등의 기존 열 투영·생성 정책은 그대로 따른다. 참조할 수 없는 빈 키에 거짓 lineage를 만들지 않는다. 저장/복원/재실행과 facet의 상속 데이터도 입력 셀을 잃지 않는다. 정상 이름만 가진 기존 프로그램의 저장 내용과 렌더 결과는 그대로다. 이전 런타임은 새 빈 키 프로그램을 읽을 수 없으며, 이 새 입력 허용 범위는 새 런타임을 필요로 한다.

## 구현 후 필수 검증

추론·명시 스키마, 빈 데이터, 빈 문자열/공백 이름, 값이 있는 미사용 열, nullable·optional 및 중복 이름, revision·행 보존 변환·기존 집계 투영·저장/복원·facet을 검사한다. 빈 필드 참조와 빈 리소스 ID가 계속 거부되는지 부정 테스트한다. 실패 원자성과 이전 프로그램·입력의 불변성을 확인한다. Full/Basic·타입·현재 계약·공개 문서를 동기화하고 정상 이름의 기존 렌더 회귀를 실행한다.

## 승인 범위 밖

빈 필드 참조 허용, 자동 이름 변경, 새 schema 버전, 패키지 배포·PR·문서 배포는 포함하지 않는다. 공개 결정이므로 사용자 승인 전에는 구현하지 않으며 다른 차트 작업은 계속한다.

## 구현 결과
